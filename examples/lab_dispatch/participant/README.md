# LINKLAB — 공동 시험실 작업 편성 서비스

> 연습용 창작 과제 v1.0 · 모든 조직·인물·수치·작업은 합성 자료입니다.
> 실제 시험의 원문·예상 정답이나 특정 회사의 운영 규정을 재현하지 않습니다.

## 1. 의뢰 배경

나래소재는 북부·남부 사업장에서 신소재 시편의 공용 시험장비를 운영합니다. 시험실은 생산팀, 연구팀, 품질팀의 요청을 함께 받습니다. 장비는 네 대뿐인데 요청은 이메일, 팀별 시트와 당일 전화로 들어옵니다. 현재 담당자는 전날 계획을 복사한 뒤 요청을 끼워 넣습니다. 예약표에는 빈칸이 있어도 장비의 재료 계열을 바꾸거나 작업자가 준비 작업을 할 수 없어 실제로는 사용할 수 없는 시간이 있습니다.

지난달에는 처리량 보고서상 여유가 있었는데도 납기를 놓쳤습니다. 다른 날에는 두 장비의 작업 시작 시각을 나란히 잡았다가 준비 작업을 하는 사람이 한 명이라 현장에서 순서를 다시 정했습니다. 야간조 작업을 다음 날짜로 옮겨 집계하면서 같은 요청이 두 번 나타난 적도 있습니다. 이번에는 입력 자료와 편성 결과를 연결하여 운영자가 이유를 설명할 수 있는 서비스를 만들려고 합니다.

가상 담당자는 **김도윤 선임 / 공동시험실 운영**입니다. 파일의 업무상 의미, 운영 메모의 적용 범위, 기존 예약 처리에 관해 질문할 수 있습니다. 담당자는 최적화 알고리즘이나 정답 일정을 제공하지 않습니다. 자료를 읽다가 발견한 충돌과 해석 차이를 구체적으로 물어보세요. 넓은 업무 질문도 가능하며 특정 암호나 정확한 키워드가 필요한 인터뷰는 아닙니다.

## 2. 이번에 만들 것

운영자가 미리 준비된 CSV 묶음을 선택하고 검증한 뒤, 기간과 운영 조건을 지정하여 작업을 장비와 시각에 배정하는 웹 서비스를 만드세요. 요청자는 자신의 요청이 언제 어디에서 처리되는지, 늦거나 배정되지 않았다면 어떤 제약 때문인지 확인합니다. 핵심은 **대체 가능한 장비, 순서에 따른 준비시간, 공동 작업자, 선행 작업과 기존 예약을 함께 고려하는 편성 로직**입니다.

연습 권장 시간은 4시간입니다. 시간을 넘겨도 작업을 숨기거나 성공으로 표시하지 말고 실제 구현 범위와 남은 범위를 기록하세요. 기술 스택은 자유입니다. 이번 자료는 시작 코드가 아니며, 참가자가 구현할 서비스를 포함하지 않습니다. 정확한 전역 최적해를 요구하지 않습니다. 다만 규칙을 위반한 계획을 좋은 점수라는 이유로 채택해서는 안 됩니다.

## 3. 운영자가 수행하는 업무

### 데이터셋 검증과 적용

운영자는 `data/provided`와 사전에 준비한 다른 폴더 중 하나를 고릅니다. 파일 업로드나 시스템 파일 선택창은 사용하지 않습니다. 데이터셋은 열 개 CSV와 `manifest.json` 전체가 하나의 버전입니다. 일부 파일만 바뀌어도 실제 내용을 읽어야 합니다. 파일 이름이나 데이터셋 이름에 따라 결과를 미리 정하지 마세요.

필수 열, 값 형식, 고유 ID, 참조 관계, 기간, 양수 시간, 시간 구간, 유효한 상태를 확인합니다. 같은 ID가 중복되거나 없는 장비를 참조하면 문제 파일과 행 또는 ID를 알려주세요. 입력 오류와 입력은 유효하지만 배정할 수 없는 상황은 구분합니다. 선행 관계의 순환이나 불가능한 참조는 입력 오류입니다. 무엇이 편성 대상인지, 기록된 상태를 어떻게 해석하는지는 운영 자료를 함께 살펴보세요.

검증에 실패하면 현재 적용 데이터와 게시 계획을 보존합니다. 검증 성공 뒤 적용은 한 번에 수행합니다. 적용한 버전과 다른 계획은 과거 참고 자료임을 표시하고 현재 결과로 내보내지 않습니다. 검증 후 적용 전에 파일이 바뀐 경우 재검증하거나 검증한 불변 사본을 적용해야 합니다.

### 편성 조건과 실행

기본 기간은 manifest의 전체 업무 기준일 범위입니다. 그 안에서 연속된 기간을 선택할 수 있어야 합니다. 운영자는 준비 여유 시간(기본 0분, 0~30분 정수), 탐색 제한 시간(기본 10초, 1~60초 정수)을 바꾸어 다시 편성할 수 있습니다. 준비 여유는 각 작업의 준비 구간에 더해집니다. 담당자와 확인한 규칙은 해당 계획의 조건으로 보존하세요.

각 편성 대상 작업은 한 장비에서 연속 처리하며 분할·중복·사업장 간 이동은 허용하지 않습니다. 다른 작업의 처리 구간과 준비 구간, 장비 사용 가능 구간, 작업자 제약, 선행 관계, 납기 규칙과 고정 예약을 모두 고려합니다. 전처리나 입력 수정으로 어려운 작업을 조용히 버리지 마세요. 규칙이 애매하면 원본과 질문·답변 근거를 남기고 해석이 확정된 범위에서 구현합니다.

운영자는 실행 중 상태를 확인하고 완료 후 결과를 비교할 수 있어야 합니다. 탐색 제한에 도달한 것과 실현 불가능함을 입증한 것은 다릅니다. 전체 계획이 검증되지 않았으면 게시하지 않습니다. 미배정 또는 제약 위반이 남은 결과는 진단 초안으로 보관할 수 있지만 요청자에게 확정 일정으로 보여주면 안 됩니다. 실패한 새 실행은 마지막 게시 결과를 덮어쓰지 않습니다.

### 결과 확인과 게시

장비별 시간축에서 준비·처리·고정 예약을 구분하고, 작업을 선택하면 사업장, 요청자, 우선순위, 선행 작업, 준비시간 근거, 지연 여부를 확인하게 하세요. 지도는 필요하지 않습니다. 날짜 필터가 업무일을 기준으로 하는지 실제 시각을 기준으로 하는지 화면에 명시합니다. 자정을 넘긴 작업을 잘라서 다른 작업으로 만들지 마세요.

최적화 기준은 운영 효율과 요청자의 납기 영향을 함께 설명해야 합니다. 우선순위를 어떻게 해석할지, 무엇을 필수 제약으로 둘지는 담당자에게 확인할 수 있습니다. 적어도 지연 작업 수, 총 지연 분, 총 준비 분, 완료 작업 수를 보여주세요. 기준선과 개선 계획을 같은 데이터·조건으로 비교하고 지표 하나를 개선하면서 악화된 지표도 드러내세요. 과거 실적은 참고 자료이며 이번 요청의 완전한 대체 자료라고 가정하면 안 됩니다.

게시된 계획은 수정하지 않고 새 계획으로 남깁니다. 데이터나 조건이 바뀌면 다시 계산한 결과를 별도 버전으로 게시합니다. 생성 중 적용 데이터가 바뀌었다면 생성이 사용한 버전과 현재 버전의 차이를 확인하고 오래된 결과가 자동 게시되는 것을 막아주세요.

## 4. 요청자와 권한

서비스 내 로그인으로 운영자와 요청자를 구분합니다. SSO는 필요 없습니다. 운영자는 전체 데이터 선택·편성·게시·내보내기를 수행합니다. 요청자는 날짜와 자신의 요청 ID로 본인 일정만 조회합니다. 다른 사람의 ID를 API에 직접 넣더라도 타인의 요청 상세를 볼 수 없어야 합니다. 계정과 요청자의 대응 관계는 구현자가 초기 데이터로 마련하고 실행 안내에 접속 절차를 쓰세요. 담당자 에이전트는 제품의 로그인 사용자나 자동 채점자가 아닙니다.

요청자에게 처리 전·진행 중·완료 표시는 시간표 기준 추정임을 알려주세요. 장비 실측 상태나 실제 완료 보고로 표현하지 않습니다. 게시 전, 해당 기간 요청 없음, 미배정, 이전 버전만 존재함을 서로 구분합니다.

## 5. 저장과 운영 준비

입력 버전, 설정, 생성 결과, 게시 상태와 계정을 DB에 보관합니다. 서버 재시작 후에도 게시 결과가 남아야 합니다. DB 종류는 자유입니다. 비밀번호·DB 연결·포트는 환경변수로 주입하고 값 없는 `.env.example`을 포함하세요. 비밀번호 원문을 로그나 내보내기에 포함하지 않습니다.

헬스체크 엔드포인트, 빈 DB 준비 절차, 컨테이너 실행용 Dockerfile을 제공합니다. 실제 클라우드 배포는 하지 않습니다. 장비 제어, 실시간 센서, 비용 산정, 이동 경로, 모바일 전용 화면, 사내 승인 시스템은 범위 밖입니다. 외부 API 키나 외부 최적화 서비스가 없어도 수행할 수 있어야 합니다.

## 6. 내보내기와 검증

`EXPORT_SCHEMA.md`의 JSON을 화면에 표시하고 복사할 수 있게 하세요. 파일 저장창을 열지 않습니다. 출력에는 원본 버전과 조건, 작업별 시각, 준비 작업자, 고정 여부와 미배정 사유가 있어야 합니다. 내부 알고리즘 객체를 그대로 직렬화하지 말고 계약에 맞는 출력으로 만드세요.

생성기와 별개의 검사에서 누락·중복, 장비/작업자 중첩, 시간창, 방향별 준비시간, 고정 예약 보존, 선행 관계를 확인하세요. 생성기와 같은 정렬·계산을 다시 실행해 결과가 같다는 것만으로 검증을 대신하지 않습니다. 데이터 한 행을 바꾼 정상 변화, 잘못된 참조, 경계 시각, 자정을 넘는 작업을 포함해 확인합니다. 직접 확인하지 않은 동작은 통과로 적지 마세요.

## 7. 자료의 관계와 제출물

`inbox/`는 실제 업무 인수인계처럼 시점과 목적이 다른 파편 문서입니다. 제목의 날짜가 최신이라는 이유만으로 모든 규정을 덮어쓰지는 않습니다. 숫자와 표현이 충돌하면 담당자에게 적용 범위를 확인하고 답변을 근거로 보존합니다. 원문 파일은 수정하지 않고 요구 추출과 결정은 별도 `requirements.md`에 작성하세요.

필수 산출물은 구현 코드, 재현 가능한 추가 데이터셋, `requirements.md`, `HOW_TO_RUN.md`, `AI_COLLABORATION.md`, `.env.example`, Dockerfile입니다. `requirements.md`에는 요구 ID·조건·원문/실제 답변·구현/검사 위치·상태를 연결하세요. `HOW_TO_RUN.md`에는 설치·DB 준비·실행·역할별 로그인·데이터 변경·오류 재현·내보내기·검사·가정과 한계를 씁니다.

`AI_COLLABORATION.md`에는 (1) 실제로 까다로웠던 조건과 조치, (2) AI 결과를 의심하고 확인한 근거, (3) 지시나 수정 뒤 달라진 동작과 미검증 범위를 씁니다. 실제로 하지 않은 경험이나 검사를 꾸며 쓰지 않습니다. 이 README와 inbox는 제공 원문으로 보존합니다. 담당자 질문 횟수 자체가 점수는 아닙니다. 중요한 해석을 실제 데이터와 연결하고 결과로 검증했는지가 중요합니다.
