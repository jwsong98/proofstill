# 화면·상태 흐름

- [인터뷰](../proofstill-interview/SKILL.md)에서 정제한 의도·확정 정책·기존 화면을 받아 UX 디자이너 역할로 사용자 여정을 그린다. 개발 브리핑 이후 이번 구현에 필요한 범위만 정한다. 기존 요구·흐름이 명확하면 재인터뷰 없이 재사용하고 전체 화면 설계가 끝날 때까지 구현을 기다리지 않는다. 사용자 범위·정책을 바꾸는 미정 결정은 인터뷰로 돌리고, 제안을 확정 요구로 바꾸지 않는다.
- 흐름을 구현하려면 중요한 기술 결정이 필요할 때 [시니어 개발자 인터뷰](../proofstill-engineer/SKILL.md)에 넘긴다. 기술 제약 때문에 사용자 행동·정책이 달라지면 해당 결정을 사용자에게 받고 흐름을 갱신한다.
- 기본 산출물은 렌더링되는 Mermaid 흐름도 하나다. 작은 기능은 보통 4~8개 상태로 시작하고 필요한 분기만 확장한다. 각 노드에 짧은 상태 ID, 화면/패널 이름, 보이는 핵심 정보·조작 요소를 넣고 화살표에는 사용자 행동 또는 시스템 결과를 적는다. API 호출 순서나 화면 이름만 나열하지 않는다.
- 같은 화면의 입력 중·처리 중·오류·완료도 사용자에게 다르게 보이면 별도 상태로 나타낸다. 조회 기능의 로딩·빈 결과·오류, 변경 기능의 저장 중·실패 후 복구·취소·재진입 중 해당 요구에 필요한 경로를 포함한다. 무관한 상태를 형식적으로 늘리지 않는다.
- 사용자가 무엇을 보고 누를 수 있는지, 처리 중 가능한 행동, 실패했을 때 남는 입력과 복구 경로를 눈으로 따라갈 수 있어야 한다. 배치 자체가 중요한 경우에만 작은 와이어프레임을 덧붙이고 큰 목업·별도 웹 페이지는 기본 산출물로 만들지 않는다.
- 상태 수명은 다이어그램 아래 `유지 / 임시 / 정리` 최대 몇 줄로 붙인다. 노드에 이미 표현한 내용은 반복하지 않는다. 기능 경계·화면 경계·상태 소유를 함께 정하고 파생값·재조회 데이터의 중복 보관을 줄인다.
- 작업 중에는 기존 임시 brief에 흐름을 함께 유지한다. 같은 설계의 IA 문서·상태표·화면별 설명서를 별도로 만들지 않는다. 기준 고정 시 다이어그램과 필요한 수명 조건을 기능 정의의 context에 보존해 독립 리뷰에도 전달하고, 이후 수정은 기준 변경 절차를 따른다.
- 복잡한 상태 수명·복구·경계가 핵심 위험이거나 기존 계약이 있으면 확정 흐름을 실행 가능한 상태머신 계약으로 [개발 스킬](../proofstill-develop/SKILL.md)에 넘긴다. 다이어그램의 상태 ID를 `state.states` 키로, 전이 ID를 `state.transitions` 키로 사용하고 `initial`, 전이별 `from/to/operation`, 상태별 `feature/screen/required/optional`을 정한다. 같은 화면의 입력 중·처리 중·실패는 서로 다른 상태 ID로 유지한다. 전이의 `preserve/drop`으로 합의한 수명을 표현한다. 기준 JSON을 다이어그램과 다른 흐름으로 작성하지 않는다.
- 상태머신 계약을 사용하는 경우 앱 snapshot의 `state_id`와 `Flow.transition(..., transition_id=전이ID, state=앱.snapshot)`으로 실제 실행을 연결하고 check의 `trace_expectation`에 계약 파일을 지정한다. 요구사항에 중요한 경로는 해당 check의 `required_transitions`로 실행 누락을 거부한다. 미실행 분기는 검증 완료로 간주하지 않는다. 최종 독립 리뷰에서 복구 경로·누락 전이 및 실제 화면·상태·저장소 결과를 함께 대조한다. 흐름도는 설계이며 클릭 실행 증거는 별도다.

- 단순 화면은 직접 모듈·통합/UI 검사로 요구를 확인할 수 있으면 별도 상태머신·Trace를 추가하지 않는다. 설계 그림만으로 실행 검증을 대체하지 않는다.
