# 관심사별 커밋

커밋 하나는 하나의 의도를 설명하고, 그 의도를 실현하는 변경만 포함한다. 개발 중 완결된 관심사마다 로컬 커밋한다. push·배포·기존 이력 재작성 권한은 포함하지 않는다.

## 메시지

`type(scope): 목적`을 쓴다. scope는 기능·도메인·패키지 경계이며 불필요하면 생략한다.

| 태그 | 목적 |
|---|---|
| feat | 새 기능 제공 |
| fix | 잘못된 동작 바로잡기 |
| refactor | 동작을 유지하며 구조 개선 |
| perf | 성능 개선 |
| test | 검사 보강·정정 |
| docs | 문서 개선 |
| build | 빌드·의존성 관리 |
| ci | CI 작업 개선 |
| style | 의미 변화 없는 서식 정리 |
| chore | 위 분류에 속하지 않는 유지보수 |
| revert | 이전 변경 되돌리기 |

- 제목은 전체 72자 이내, 가능하면 50자 안팎으로 쓴다. 한글 목적 표현을 기본으로 하되 저장소의 명시된 언어 규칙이 있으면 따른다. 영어는 명령형으로 쓴다. 마침표·이모지는 붙이지 않는다.
- 파일·함수·작업 순서를 나열하지 말고, 대상과 바뀌는 결과·이유를 드러낸다. `수정`, `개선`, `작업 완료`만으로 끝내지 않는다.
- 기본은 제목 한 줄이다. 제목만으로 알 수 없는 이유·제약이 있을 때만 빈 줄 뒤 1~2문장을 더한다. 로그·검사 목록·장문 보고를 본문에 붙이지 않는다.
- 호환성을 깨면 `type(scope)!: 목적`과 필요한 이행 설명을 남긴다. 실제 요구·이슈 연결이 필요하면 `Refs: 요구ID` 또는 저장소의 footer 규칙을 사용한다. 존재하지 않는 번호·승인·검증 결과를 만들지 않는다. 필수 trailer는 보존한다.

```text
feat(tasks): 마감일로 할 일을 조회할 수 있게 한다
fix(auth): 만료된 세션의 재사용을 막는다
refactor(orders): 할인 정책을 독립적으로 바꿀 수 있게 한다
test(orders): 중복 결제 방지 조건을 검증한다
```

`feat: API 구현 및 UI 수정 및 포맷 정리`처럼 여러 목적을 묶지 않는다. `fix(auth): if문과 캐시 키 수정`처럼 구현 수단만 적지 않는다.

## 작업 중 커밋하는 순서

- 모든 구현 작업자는 이 스킬을 읽고 `한 관심사 구현 → 변경 위험에 맞는 확인 → 명시한 파일 stage → diff 확인 → 커밋`을 마친 뒤 다음 관심사로 이동한다. 전체 작업이 끝난 뒤 변경을 역으로 나누는 방식을 기본으로 삼지 않는다.
- 다른 관심사의 수정을 같은 파일에 쌓지 않는다. 정상 흐름에서는 해당 관심사의 파일만 `git add -- <경로...>`로 추가한다. hunk 분리는 이미 섞여 있는 기존 변경을 안전하게 분리해야 할 때의 예외다.
- 작업을 위임할 때 스킬 경로, 이번 관심사, 담당 파일, 검사 명령, 커밋 시점을 함께 전달한다. 구현 작업자는 커밋 해시·제목·검사 결과를 반환한다. 읽기 전용 조사·독립 검증 작업자는 파일 수정·커밋을 하지 않는다.
- 같은 저장소에서 여러 작업자가 일하면 index와 HEAD를 공유하므로 stage·커밋은 동시에 하지 않는다. 대표 작업자가 순서를 조정하고 한 작업자가 stage부터 검사·커밋까지 마친 뒤 다음 작업자에게 넘긴다. 다른 작업자의 미커밋 코드가 필요하면 선행 관심사의 커밋을 기다린다. 미완성 변경을 모아 마지막에 한꺼번에 커밋하지 않는다.

## 작게 나누는 기준

- 변경 전에 이번 관심사를 한 문장으로 정하고 관련 요구·코드·검사를 고른다. 별도 커밋 계획서를 만들 필요는 없다.
- 독립적으로 설명·검토·되돌릴 수 있고 빌드도 유지되는 가장 작은 단위를 찾는다. 파일 수·줄 수를 줄이려고 동작을 조각내지 않는다.
- 기능 코드와 그 회귀 검사, 필요한 계약·migration·생성물·lockfile은 같은 의도이면 함께 넣는다. backend와 UI도 함께 있어야 동작한다면 묶는다. 파일 종류별 분리는 목표가 아니다.
- 독립적인 리팩터링·포맷·의존성 갱신·다른 버그 수정은 분리한다. 선행 리팩터링이 필요하면 동작을 유지하는 커밋을 먼저 만들고 기능을 뒤에 둔다.
- 실패하는 테스트만 먼저 커밋하거나, 다음 커밋의 미완성 코드에 기대어 빌드되는 상태를 남기지 않는다. Red 검사는 작업 중 실행하고 수정과 함께 Green 상태로 커밋한다.

## 커밋 전 확인과 실행

1. `git rev-parse --show-toplevel`, `git status --short`, `git diff`, `git diff --cached`, 최근 로그와 저장소 지침을 읽는다. Git 저장소가 없으면 초기화하거나 상위의 무관한 저장소에 커밋하지 말고 미커밋 상태와 이유를 알린다.
2. 기존 staged·unstaged·untracked 변경과 이번 위임 범위를 대조한다. 타인의 변경은 임의로 포함·해제·삭제하지 않는다. 기존 staged 변경의 소유·의도가 불명확하면 커밋 전에 그 부분만 확인한다. 자동 stash·reset·clean으로 작업 상태를 바꾸지 않는다.
3. 이번 관심사만 변경된 파일을 `git add -- <경로...>`로 stage한다. 이미 같은 파일에 여러 의도가 섞여 있다면 예외적으로 `git add -p`로 필요한 hunk만 분리하고, 이후에는 관심사마다 커밋해 혼입을 예방한다. `git add .`, `git add -A`, `git commit -a`로 일괄 반영하지 않는다. 비밀·로컬 데이터·임시 brief·무관한 산출물은 제외한다.
4. `git diff --cached --check`, `git diff --cached --stat`, **전체 staged diff**를 확인한다. 제목의 의도로 모든 hunk를 설명할 수 있어야 한다. 빈 diff는 커밋하지 않는다.
5. 변경 위험과 기존 검증 근거를 보고 필요한 확인만 고른다. 커밋마다 테스트·타입 검사·빌드를 무조건 실행하지 않는다.
   - 문구·문서·작은 스타일 변경은 diff와 관련 형식·링크·화면의 직접 확인으로 끝낼 수 있다. 동작 변경은 영향받는 관련 검사만 실행한다. 빌드·의존성·모듈 연결 변경처럼 빌드 결과에 영향을 주는 경우에만 빌드를 실행한다.
   - 전체 검사와 최종 빌드는 필요한 기능 묶음 단위로 수행한다. 이미 통과한 검사는 관련 소스 변경·실패·구체적인 우려가 없으면 반복하지 않는다. 커밋 분리나 stage 변경만으로 검증 근거를 무효화하지 않는다. 이미 구현된 변경의 커밋·push 요청도 기존 검증 근거부터 확인한다.
   - 검사는 현재 작업 디렉터리에서 수행한다. 검사용으로 코드를 임시 폴더에 복사·내보내기하거나 별도 checkout·worktree·clone을 만드는 행위는 금지한다. `git checkout-index --prefix`, archive 추출, 복사 후 의존성 연결 등으로 우회하지 않는다.
   - unstaged·untracked 변경이 검사에 영향을 주면 실제 검사한 작업 트리 범위와 한계를 짧게 밝힌다. 검사하지 않은 개별 커밋 상태를 검사했다고 주장하지 않는다. 임시 복사나 불필요한 재검사로 이를 증명하려 하지 않는다. 하네스 독립 리뷰는 개발 스킬의 기능 묶음 기준을 유지한다.
   - 실행한 검사 실패와 환경 문제는 통과로 보고하지 않는다. 변경과 관련된 실패는 수정하거나 해당 커밋을 보류하고, 무관한 실패는 근거와 한계를 알린다. hook 실패는 우회하지 않는다. 새 lint·hook 도입을 기본 작업으로 늘리지 않는다.
6. `git commit -m '<제목>'`으로 로컬 커밋한다. 본문이 필요하면 실제 줄바꿈을 보존한 파일을 `git commit -F <파일>`로 전달한다. 서명·사용자 정보·hook·설정을 임의로 바꾸거나 `--no-verify`로 우회하지 않는다. 기존 커밋 amend·rebase·squash는 별도 요청 없이는 하지 않는다.
7. `git show --stat --oneline HEAD`, 필요한 전체 diff와 `git status --short`를 대조해 의도·파일 범위와 남은 변경을 확인한다. 결과는 `짧은 해시 · 제목 · 실제 검사 결과 · 남은 변경/한계`만 간결하게 전한다. 실패 시 성공한 커밋과 미커밋 변경을 구분한다.

## 참고한 관례

다음은 설계 근거이며 실행 중 매번 조회할 필요는 없다. 대회 문제·코드·결과를 외부로 보내지 않는다.

- [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/): type, 선택 scope, 짧은 설명과 호환성 변경 표기.
- [LangChain 커밋 이력](https://github.com/langchain-ai/langchain/commits): `fix(core)`·`feat(core)`처럼 분류와 범위를 드러내는 제목.
- [Spring Boot 팀 관례](https://github.com/spring-projects/spring-boot/wiki/Team-Practices#commit-messages): 짧은 제목, 명령형, 구현 방법보다 무엇을 왜 바꾸는지 설명. type 태그를 필수로 쓰는 프로젝트라는 뜻은 아니다.
- [FastAPI 커밋 이력](https://github.com/fastapi/fastapi/commits): 이모지 분류와 짧은 동작 중심 제목. 여기서는 분류 목적을 참고하고 텍스트 태그로 통일한다.

- 코드·문서의 변경 기준은 Git 커밋만 사용한다. 검증용 코드 복사·내보내기·별도 checkout/worktree/clone과 별도 소스·내용 해시 기반 버전·게이트를 만들지 않는다. 현재 작업 디렉터리에서 필요한 검사만 수행하고 파일 해시·수정 시각·Git 커밋 비교로 검사·리뷰의 최신성이나 통과를 자동 결정하지 않는다. Git은 버전 기록에만 사용하고, 실행 결과는 관측 시점·검사 범위·한계로 설명한다.
