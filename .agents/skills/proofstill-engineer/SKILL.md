# 시니어 개발자 인터뷰

- [기획 인터뷰](../proofstill-interview/SKILL.md)의 원래 요청·확정 요구·제약과, 화면이 있으면 [UX 흐름](../proofstill-ux/SKILL.md)을 읽는다. 새 프로젝트 생성, 스택 도입·교체, 모듈 경계나 데이터 소유의 중요한 변경 전에 수행한다. 기존 합의 안의 작은 수정은 결정을 재사용하고 불필요한 재인터뷰를 하지 않는다.
- 먼저 저장소·실행 환경·외부 연동·제공 도구를 조사한다. 구현 가능성을 확인한 사실, 아직 검증하지 않은 가정, 기술적 장애로 구분한다. 불확실성을 해소할 최소 실험은 임시 위치에서 수행하고 결과·한계를 설명한다. 실험 성공을 제품 전체의 구현 가능성이나 사용자 동의로 확대하지 않는다.
- 사용자가 결정할 것은 비용·납기·운영 부담·데이터 보관·기능 품질의 절충, 중요한 책임 경계와 기술 선호다. 에이전트는 조사·대안·추천과 상세 구현을 맡는다. 사용자가 판단할 결과 차이를 설명한 뒤 선택을 받으며, 기술 지식을 시험하거나 구현 방법을 전부 사용자에게 떠넘기지 않는다.
- 한 번에 중요한 질문 1~3개만 묻는다. 각 질문은 구체적인 결정, 현실적인 선택지, 사용자에게 미치는 차이, 추천과 이유를 담고 자유 답변을 허용한다. 예를 들어 “백그라운드 작업을 별도 프로세스로 두면 재시도가 쉽지만 운영 대상이 늘어납니다. 첫 버전은 단일 프로세스를 추천하는데, 긴 작업 중에도 다른 요청을 반드시 처리해야 하나요?”처럼 실제 요구와 연결한다. 답변에 따라 다음 질문을 조정한다.
- 핵심 사용자 흐름이 어디서 실행되고 무엇을 읽고 쓰는지 설명하며 구현 가능성과 아키텍처를 논의한다. 필요한 모듈·책임·의존 방향·데이터 소유·외부 경계·실패 복구를 작은 구조도나 몇 줄로 제시한다. 기술 제약으로 요구 변경이 필요하면 선택지와 영향을 사용자에게 돌리고 [기획 인터뷰](../proofstill-interview/SKILL.md)·UX에 반영한다. 기능을 조용히 축소하거나 미래 확장을 위한 빈 계층을 만들지 않는다.
- 구현 가능성과 주요 책임 경계에 대한 사용자 결정을 받은 뒤, 그 조건에 맞는 개발 스택 후보와 폴더 구조안을 제시한다. 기존 스택·제공 템플릿도 후보일 뿐 확정 근거가 아니다. 후보별 적합성·제약과 추천 이유를 설명하고, 사용자의 선택 또는 명시적으로 위임한 범위에 따라 스택과 구조를 확정한다. 폴더안에는 실제 필요한 코드의 책임과 의존 관계가 드러나게 한다.
- 사용자의 실제 답변·선택·위임 범위를 근거로 남긴다. 추천·그림 제시·“진행하겠다”는 에이전트의 선언·무응답은 결정이 아니다. 답변이 일부만 확정하면 나머지는 미정으로 유지한다. 앞선 결정과 충돌하거나 비용·운영·범위를 바꾸는 새 사실이 생기면 영향받는 결정만 다시 논의한다.
- 스택·구조에 영향을 주는 사용자 결정이 남아 있으면 그에 의존하는 패키지 설치, 스캐폴드 실행, 제품 폴더 생성과 구현은 기다린다. 자료 조사·호환성 확인·의존하지 않는 작업은 계속한다. 질문 뒤에는 답변을 받을 기회를 보장하고 시간 경과를 선택으로 간주하지 않는다.
- `scaffold`는 정해진 템플릿을 생성하는 도구다. 실행 전에 선택한 스택·앱 구성·폴더 구조와 호환되는지 확인한다. 맞지 않으면 차이를 설명하고 수동 구성 또는 템플릿 변경을 논의한다. “Proofstill로 프로젝트 만들어줘”만으로 기본 스택 전체를 선택했다고 해석하지 않는다. CLI를 직접 실행한 사용자의 명시적 옵션은 그대로 존중한다. 이 인터뷰는 CLI의 자동 차단기가 아니다.
- 기존 임시 brief에 `확인 사실 / 사용자 결정과 답변 근거 / 제안·가정 / 미정 결정과 영향 / 다음 행동`만 짧게 유지한다. 새 인터뷰이면 `.proofstill/work/intake-<작업ID>/brief.md`를 사용한다. 프로젝트 경로를 만들기 전에는 현재 작업 위치에서 기록하고 제품 디렉터리를 미리 만들지 않는다. 별도 아키텍처 문서·대화록을 기본으로 추가하지 않는다.
- 종료 조건은 구현 가능성의 근거·남은 위험, 주요 책임 경계, 스택·폴더 구조가 실제 답변이나 명시적 위임으로 확정되고 이에 의존하는 사용자 결정이 남지 않은 상태다. 충분한 답변 뒤 형식적인 재승인을 요구하지 않는다. [개발 스킬](../proofstill-develop/SKILL.md)에 확정 결과·근거·위임 범위·미검증 위험을 전달하고, 그 뒤 합의한 구조를 생성한다. 기능 정의의 `context`에 필요한 결정과 실제 답변 근거를 보존하며 변경 중인 brief를 고정 검토 입력으로 직접 연결하지 않는다. 정리·보존은 개발 스킬을 따른다.
